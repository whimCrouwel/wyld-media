# 設計書: ライターと環境のためのプラットフォーム(MVP)

日付: 2026-07-06
ステータス: 承認済み(設計)

## 概要

環境・自然をテーマにした記事プラットフォーム。ライターと、環境活動を行う事業者(サービスプロバイダー)をつなぐマッチング要素を持つ。プロバイダーはプラットフォーム外でライターに記事執筆を依頼でき、依頼記事は「Featured article」として優先表示される。

- ライターの価値: 記事執筆の受注機会
- プロバイダーの価値: 自身の活動の露出
- MVP方針: デザインなし・骨組みのみ。決済機能なし(依頼・支払いは当事者間で完結)

## アーキテクチャ

| 層 | 技術 | 役割 |
|---|---|---|
| 公開サイト | Astro(完全静的ビルド)+ Vercel | 記事・ライターページの高速表示、SEO |
| CMS画面 | 同一 Astro プロジェクト内のクライアントレンダリングページ | ログイン、投稿、プロフィール編集、管理 |
| DB・認証 | Supabase(Postgres + Auth + RLS) | ユーザー・記事・設定の管理、権限制御 |
| サーバー処理 | Supabase Edge Functions(2つのみ) | ①ユーザー招待(管理者専用) ②R2署名付きURL発行 |
| 画像 | Cloudflare R2 | 画像ストレージ |

- **別バックエンドは作らない。** CMS画面はブラウザから Supabase JS クライアントで直結し、権限は RLS で強制する。
- **再ビルド方式**: 記事の公開・更新・削除時に Supabase Database Webhook が Vercel の Deploy Hook を叩き、静的サイトを自動再ビルドする。投稿頻度が低い(通常投稿は1ユーザーあたり10日に1回)ため再ビルド回数は少なく、この方式で成立する。
- 静的ビルドは Supabase の service role キーで全公開データを取得して行う。

## データモデル

```
profiles
├ id                … Supabase Auth users と 1:1(内部ID、非公開)
├ role              … 'admin' | 'writer' | 'provider'
├ slug              … 公開ページ用URL文字列(ユニーク)
├ name              … 表示名
├ bio               … 自己紹介
├ homepage_url
├ sns_links         … jsonb
├ price_info        … 料金設定(ライター用、任意)
├ contact_url       … 相談窓口リンク(ライター用、任意)
└ commission_code   … 依頼者コード(providerのみ。推測困難なランダム文字列、ユニーク)

articles
├ id
├ author_id         → profiles.id
├ slug              … ライターが入力する英字スラッグ(ユニーク制約)
├ title
├ body              … Markdown のまま保存
├ cover_image_url   … Cloudflare R2 のURL
├ status            … 'draft' | 'published'
├ published_at
└ commissioned_by   → profiles.id(null可。非null = 依頼記事)

settings(1行のみ)
├ post_interval_days … 通常投稿の最小間隔(初期値: 10)
└ featured_count     … Featured枠の表示件数(初期値: 3)
```

### 主要ルール

- **Featured(件数制)**: トップページの Featured 枠には「最新の依頼記事 `featured_count` 件」を表示。枠から外れた依頼記事は通常記事として一覧に並ぶ。
- **投稿頻度制限**: `commissioned_by` が null の記事の公開は、同著者の直近の通常公開記事から `post_interval_days` 日の経過が必要。**依頼記事は制限の対象外。** DBトリガーで強制する(クライアント改ざんでは回避不可)。
- **依頼者コード**: 内部ID(Auth UUID)とは別の公開用コード。プロバイダーがプラットフォーム外の交渉時にライターへ伝え、ライターが記事エディタで入力する。入力時に実在チェックを行う。
- **記事 slug**: 公開時に必須。小文字英数字とハイフンのみ。エディタで形式チェックと重複チェックを行い、DB側にもユニーク制約を持つ。

## 権限設計

### 権限マトリクス

| 操作 | admin | writer | provider |
|---|---|---|---|
| ユーザーの登録・削除・ロール設定 | ✅ | ❌ | ❌ |
| 自分の記事の作成・編集・削除 | ✅ | ✅ | ✅ |
| 他人の記事の編集・下書き閲覧 | ✅(運営対応用) | ❌ | ❌ |
| 自分のプロフィール編集 | ✅ | ✅ | ✅ |
| 自分の role / commission_code の変更 | ✅ | ❌ | ❌ |
| サイト設定(投稿間隔・Featured件数)の変更 | ✅ | ❌ | ❌ |

※ 公開済み記事は静的サイトで誰でも閲覧できる。「他人の記事を閲覧不可」が実質意味を持つのは下書き。

### RLS ポリシー(要点)

```
profiles: SELECT 自分の行 / adminは全員分
          UPDATE 自分の行のみ(role・commission_code はトリガーで変更拒否)
          INSERT/DELETE adminのみ

articles: SELECT author_id = auth.uid()(全ステータス)/ adminは全件
          INSERT author_id = auth.uid() のみ + 頻度制限トリガー
          UPDATE/DELETE 自分の記事 / adminは全件

settings: SELECT 認証ユーザー / UPDATE adminのみ
```

### セキュリティ上の決定事項

1. **セルフサインアップ完全無効化。** ユーザー登録は管理者だけが呼べる Edge Function 経由(Function 内でも呼び出し元の role をDB照合)。
2. **認証方式は招待メール+パスワード。** 管理者がメールアドレスで招待 → ユーザー自身がリンクからパスワード設定 → 以降メール+パスワードでログイン。管理者がパスワードを知ることはない。
3. **依頼者コードの実在チェックは専用RPC(SECURITY DEFINER)。** コードが完全一致した場合のみプロバイダー名を返す。プロバイダーやコードの一覧取得は不可(列挙攻撃の防止)。
4. **role の自己昇格防止。** profiles の UPDATE で role / commission_code の変更をDBトリガーで拒否。

## 画面一覧

### 公開(静的)

- トップ: Featured枠(最新の依頼記事 N 件)+ 通常記事一覧
- 記事ページ: `/articles/{slug}`(Markdown はビルド時にHTML化)
- ライター一覧
- ライター個別ページ: `/writers/{slug}`(名前・自己紹介・HP・SNS・料金/相談窓口)

### CMS(要ログイン)

- ログイン
- ダッシュボード: 自分の記事一覧(公開済み+下書き)/ [新しい記事を作成] / [プロフィールを編集]
- 記事エディタ:
  - タイトル、slug入力(形式・重複チェック)
  - カバー画像: 選択 → Cropper.js でクロップ → ブラウザ内でリサイズ・WebP圧縮(長辺1600px・500KB目安)→ 署名付きURLで R2 へアップロード
  - 本文: マークダウンエディタ(EasyMDE、プレビュー付き)
  - 依頼者コード入力欄(入力時に実在チェック、一致すればプロバイダー名を表示)
  - [下書き保存] / [公開](公開は即時。承認フローなし)
- プロフィール編集: 名前・自己紹介・HP・SNS・料金/相談窓口
- 管理者のみ: ユーザー管理(一覧・招待・ロール設定・依頼者コード発行)/ サイト設定

## エラー処理

- 頻度制限違反・slug重複・不正な依頼者コード: 送信前にエディタで検知して表示しつつ、DB層(トリガー・制約・RPC)でも拒否する二重防御。
- 画像サイズ超過: クライアントで自動縮小。すり抜けた場合は署名付きURL発行時(Edge Function)で拒否。
- 再ビルドWebhookの失敗: MVPでは管理者が Cloudflare ダッシュボードから手動再デプロイでカバー。

## テスト方針(MVP)

- **最優先**: RLSポリシーとトリガー(頻度制限・role保護・依頼者コードRPC)のSQLレベルテスト。ここがセキュリティの本体。
- 画面はMVPでは手動確認(デザインなしの骨組みのため自動UIテストは後回し)。

## スコープ外(MVP)

- 決済・支払い機能(当事者間で完結)
- 記事の承認フロー(公開は即時)
- デザイン(骨組みのみ)
- 自動UIテスト
- 画像編集のクロップ以外の機能(回転・色調整など)
